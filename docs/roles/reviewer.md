# reviewer — 最終レビュー（観点別・並列・1 回）

全タスク完了後に、観点ごとに 1 体ずつ並列で起動する。毎タスクでは起動しない。**モデルは既定で下位で足りる**（根拠をコードの該当行とテストの出力に縛っているため）。上位モデルを観点ぶん並列に起動するとセッションのレート上限に当たって途中で止まる。
理由は 2 つ: タスク数ぶんレビューコストが積み上がること、タスク単位では見えない「つなぎ目」の欠陥（デッドロック、後続タスク前提の未実装 など）は全部そろってからでないと判定できないこと。

## 観点（1 体に 1 観点。プロジェクトで増減する）

| 観点 | 見るもの |
|---|---|
| 仕様突合 | `docs/spec/` どおりに作られているか。受け入れ条件が全部テストに落ちているか |
| 並行性 | 同時に操作されても壊れないか（ロック、整合性、デッドロック） |
| 認可 | 誰がどの操作をできるか。権限チェックの漏れ、境界でのデータ検証 |
| 機能の完結性 | 入口だけ作って終わっていないか（導線、事後処理、通知） |

## 報告の形式

指摘 1 件ごとに: 場所（パス:行）、何が問題か、**コード上の証拠**、再現手順または失敗するテスト案、重大度、修正コストの見積り（高 / 低）。

orchestrator に返す**要約**には、指摘ごとに **重大度・場所・見出し・修正コスト（高 / 低）** を必ず入れる。orchestrator は report 本文を開かない規律なので、修正コストが要約に無いと「反証を回すか」（下の条件 1）を判定できない。
orchestrator は 4 体の報告を**重複排除**してまとめる。複数の reviewer が独立に同じ箇所を報告したことは、それ自体が指摘の強い証拠。

## 反証（偽陽性を潰す）の 3 つの縛り

反証役は「反証してみて」と頼まれると反証方向に寄り、根拠が薄くても「問題ない」と書きがち。放置すると本物の不具合が偽陽性扱いで消える。そこで:

1. **回す条件を絞る**: 「報告した reviewer が 1 体だけ」**かつ**「修正コストが高い」の両方を満たす指摘だけに反証を回す。複数の reviewer が独立に見つけた指摘には回さない（実測でも、そうした指摘はすべて指摘側が正しかった）。
2. **証拠のない反証は認めない**: 根拠として認めるのはコードの該当行かテストの出力だけ。「おそらく問題ない」「一般的にはこう」は根拠にならない。
3. **白黒がつかなければ消さない**: 結論が出なかった指摘は、強度を下げて `progress.json` の未解決レビュー結果に残す。多数決も使わない。

反証役は 1 呼び出しの単価が最も高いので、条件を絞ることがコストにも効く。
