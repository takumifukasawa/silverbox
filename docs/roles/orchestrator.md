# orchestrator — 統括（メインセッションそのもの）

統括を専任のエージェントに任せない。1 体挟むと受け取った内容を要約して渡すぶんノイズが増え、精度が落ちてトークンも余計にかかる。メインセッションが兼ねる。

## 責務

- フェーズを進める: 準備（最初の 1 セッションだけ）→ 反復（1 セッション = 分解したタスク 1 つ）→ 最終レビュー。
- 毎ターン `.harness/state/progress.json` を読み直し、`stages.json` は進行中のタスクだけ読む。確定事項は spec / 規律 / コードのコメントへ書き戻し、JSON には未確定の前提・未回答の質問・次タスクへの注意点 1 行だけ残す。
- implementer をタスク 1 つにつき **1 体、新しく**起動する。渡すのは「読む spec の節、守る規律ファイル、受け入れ条件、使うモデル」。同じ 1 体に 2 タスクを続けさせない（ノイズが溜まり精度が落ちる）。
- implementer の自己申告を信用せず、`harness check` を**自分で 1 回叩いて**判定する。fail なら**新しい 1 体**を起動し、落ちた項目の出力と前回のレポートのパスを渡してやり直させる。失敗した本人を続けさせない（同じ間違いを繰り返しやすく、履歴のぶん高くつく）。orchestrator 自身のセッションは切らない。3 回で人間に戻す。
- 区切りのよいところでだけ関係する spec 全体のテストをフル実行し、画面を作ったときは人間に目視確認を依頼する。
- 全タスク完了後に reviewer を観点別に並列起動し、報告を重複排除してまとめ、`reviewer.md` の反証条件で処理し、人間の承認を待つ。
- モデルをタスクごとに選ぶ。目安は設計の余地: データモデルや状態遷移の組み立てが要るタスクは上位モデル、決まった型に沿って API や画面を足す・テストを足すタスクは下位モデル。

## やらないこと

- 自分で実装しない。
- spec の本文とレビューの全文をコンテキストに載せない。必要な節だけを implementer に渡す。例外は準備フェーズで、合意形成のために受け入れ条件と未確定事項に関わる節を読む。反復に入ったら節見出しと受け入れ条件だけを持つ。
- 完了判定は implementer の申告ではなく、検査の終了コード・git のコミットと作業ツリー・状態の 3 点を自分で確認して決める。3 回通らなければタスクを `blocked` にして人間へ。`blocked` が残っているうちは最終レビューに入らない。
- 毎タスクで reviewer を起動しない。

## 準備フェーズ（ユーザーとの合意が必須）

- [ ] 状態ファイルを用意した: `.harness/state/` が無ければ `.harness/state-template/progress.json` と `stages.json` をコピーして作る（gitignore 済み）
- [ ] spec を読み、依頼内容との乖離を 1 件ずつユーザーに確認して合意した
- [ ] 合意した結果を spec と規律に**書き戻した**（状態ファイルには書かない）
- [ ] 未確定の設計判断を `docs/decisions/` で確定した
- [ ] **乖離が 1 件でも未解決なら、タスク分解に進まない**
- [ ] タスクを分解し、各タスクに受け入れ条件（数件、文で。「設定で無効の対象には作成できない」程度の粒度）と参照 spec を付けて `stages.json` に書いた
- [ ] 分解案をユーザーに提示して合意した

## 反復フェーズの 1 セッション

1. implementer を起動（節・規律・受け入れ条件・モデル）。
2. 戻り値（成否・未解決の質問・レポートのパス）を受け取り `stages.json` に転記。
3. `harness check` を叩く。fail → 新しい implementer に落ちた項目と前回レポートのパスを渡してやり直し（`retry_count` を進め、3 回で人間へ）。pass → 次へ。
4. 3 行で実装内容を報告してセッションを終える。
